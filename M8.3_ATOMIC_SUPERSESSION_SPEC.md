## 1. Transaction Workflow

When a reviewer executes `POST /api/knowledge/articles/:id/approve` or `publish` on an article under review that has `parentArticleId`:

```mermaid
sequenceDiagram
    autonumber
    actor Reviewer as Quality Reviewer
    participant Ctrl as KnowledgeArticleController
    participant Svc as KnowledgeArticleService
    participant DB as PostgreSQL (EntityManager.transaction)
    participant Audit as AuditService

    Reviewer->>Ctrl: POST /api/knowledge/articles/:id/approve
    Ctrl->>Svc: approveAndPublish(id, dto, userId, tenantId)
    
    rect rgb(240, 248, 255)
        Note over Svc,DB: BEGIN TRANSACTION (Serializable / Repeatable Read)
        Svc->>DB: Lock & Load Child Revision (v2)
        Svc->>DB: Lock & Load Parent Predecessor (v1)
        
        Svc->>Svc: Validate Predecessor Status is PUBLISHED
        Svc->>Svc: Validate Version Invariant (v2.version === v1.version + 1)
        Svc->>Svc: Validate Tenant Invariant (v2.tenantId === v1.tenantId)
        
        Svc->>DB: UPDATE v1 SET status='SUPERSEDED', is_latest=false, superseded_by_id=v2.id
        Svc->>DB: UPDATE v2 SET status='PUBLISHED', is_latest=true, published_at=now(), reviewed_by=user
        
        Note over Svc,DB: COMMIT TRANSACTION
    end
    
    Svc->>Audit: logBusinessEvent('knowledge_article.published', v2)
    Svc->>Audit: logBusinessEvent('knowledge_article.superseded', v1)
    Svc-->>Ctrl: Return Published Revision v2
    Ctrl-->>Reviewer: 200 OK + Updated v2 Record
```

## 2. Invariants Guaranteed by Transaction Boundary

| Invariant | State on Success | State on Rollback |
|:---|:---|:---|
| **Parent Status** | `SUPERSEDED` | Remains `PUBLISHED` |
| **Parent isLatest** | `false` | Remains `true` |
| **Parent supersededById** | Set to `v2.id` | Remains `null` |
| **Child Status** | `PUBLISHED` | Remains `UNDER_REVIEW` |
| **Child isLatest** | `true` | Remains `false` |
| **Child publishedAt** | Timestamp recorded | Remains `null` |
| **Active Version Count** | Exactly 1 (`v2`) | Exactly 1 (`v1`) |
| **Audit Events** | Emitted post-commit | **Zero false events emitted** |

---

## 3. Rollback Failure Handling

If any exception occurs inside the transaction (e.g. database disconnect, lock timeout, constraint error, or unexpected validation failure):
1. TypeORM automatically triggers `ROLLBACK`.
2. Both rows revert to their pre-transaction states.
3. The method re-throws the error to the HTTP layer (yielding 4xx or 5xx).
4. No business audit events are written to `audit_logs`.
