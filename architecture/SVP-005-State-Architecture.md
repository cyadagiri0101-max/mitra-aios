# Software Verification Platform (SVP) — State Architecture

## 1. Dual State Model

SVP maintains two parallel representations of state:

```
┌──────────────────────────────────────────────────────────────────┐
│                        DUAL STATE MODEL                          │
│                                                                  │
│  ┌─────────────────────┐          ┌─────────────────────────┐   │
│  │   HUMAN STATE        │          │   MACHINE STATE          │   │
│  │   Markdown           │          │   YAML / JSON            │   │
│  │                      │          │                          │   │
│  │  - Readable by       │          │  - Parsable by           │   │
│  │    humans            │          │    machines              │   │
│  │  - Narrative         │          │  - Structured            │   │
│  │  - Contextual        │          │  - Validatable           │   │
│  │  - Meant for         │          │  - Meant for             │   │
│  │    documentation     │          │    automation            │   │
│  └─────────────────────┘          └─────────────────────────┘   │
│           │                                    │                 │
│           └──────────────┬─────────────────────┘                 │
│                          │                                       │
│                          ▼                                       │
│              ┌─────────────────────┐                             │
│              │  Synchronization    │                             │
│              │  Strategy           │                             │
│              │                     │                             │
│              │  Machine state is   │                             │
│              │  source of truth.   │                             │
│              │  Human state is     │                             │
│              │  derived from it.   │                             │
│              └─────────────────────┘                             │
└──────────────────────────────────────────────────────────────────┘
```

## 2. State Files

### 2.1 Project State

**Location:** `.ai/state/project.yaml` (machine) + `PROJECT_STATE.md` (human)

**Purpose:** Top-level project tracking — what phase are we in, what's been completed, what's next.

**Machine state format:**

```yaml
# .ai/state/project.yaml
project:
  name: Mitra3.0
  description: Software Verification Framework implementation
  version: 1.1.0
  status: ACTIVE
  current_phase: ARCHITECTURE
  completed_phases:
    - DISCOVERY
    - PLANNING
  phases:
    - id: DISCOVERY
      name: Discovery
      status: COMPLETED
      completed_at: 2026-07-07
    - id: ARCHITECTURE
      name: Architecture
      status: IN_PROGRESS
      started_at: 2026-07-08
      tasks:
        - id: SVP-ARCH
          description: Design SVP platform architecture
          status: IN_PROGRESS
```

**Human state format:**

```markdown
# PROJECT_STATE
Current Phase: Architecture
Completed: Discovery, Planning
Next: Complete SVP architecture documents
Model: Qwen3.7 Max
```

**Synchronization:** Machine state is the source of truth. Human state is regenerated from machine state at session end. Humans may update human state directly, which triggers machine state update on next read.

### 2.2 Framework State

**Location:** `.ai/state/framework.yaml` (machine) + `framework/META.md` (human)

**Purpose:** Track framework document status — which documents exist, their status, version, and layer.

**Machine state format:**

```yaml
# .ai/state/framework.yaml
framework:
  version: 1.1.0
  status: IN_COMPLETE
  layers:
    L0:
      name: Governance
      status: COMPLETE
      documents:
        - id: SVF-GOV-001
          title: Framework Charter
          status: APPROVED
          version: 1.0.0
    L1:
      name: Standards
      status: COMPLETE
      documents:
        - id: SVF-STD-001
          title: Documentation
          status: APPROVED
          version: 1.0.0
      taxonomies:
        status: MISSING
        expected: 5
        actual: 0
    L2:
      name: Methodology
      status: IN_PROGRESS
      documents:
        - id: SVF-MTH-001
          title: Audit Methodology
          status: APPROVED
          version: 1.0.0
```

**Synchronization:** Machine state is generated by scanning the framework directory. Human state (META.md) is the canonical description but should be kept in sync. When documents are added or status changes, the agent updates both.

### 2.3 Engagement State

**Location:** `.ai/state/engagement.yaml` (machine) + `engagements/{pid}/ENGAGEMENT.md` (human)

**Purpose:** Track engagement lifecycle — scope, phase, gates passed, evidence collected, findings identified.

**Machine state format:**

```yaml
# .ai/state/engagement.yaml
engagement:
  id: MITRA3
  project: Mitra 3.0 Backend
  status: PLANNING
  phase: SCOPING
  gates:
    planning: PENDING
    evidence: PENDING
    analysis: PENDING
    release: PENDING
  assurance_level: L2
  evidence_count: 0
  finding_count: 0
  started_at: null
  target_completion: null
```

**Synchronization:** Engagement state updates as work progresses. Each stage gate passed updates the state. Machine state is updated by agents during sessions.

### 2.4 Repository State

**Location:** `.ai/state/repository.yaml` (machine)

**Purpose:** Repository health and structure tracking — directory existence, file counts, integrity status.

**Machine state format:**

```yaml
# .ai/state/repository.yaml
repository:
  last_scan: 2026-07-08T12:00:00Z
  directories:
    - path: framework/governance
      exists: true
      file_count: 8
    - path: framework/taxonomies
      exists: true
      file_count: 0
  integrity:
    last_verified: 2026-07-08T12:00:00Z
    all_hashes_match: true
    mismatches: []
```

### 2.5 Next Task State

**Location:** `.ai/state/next-task.yaml` (machine) + `NEXT_TASK.md` (human)

**Purpose:** Task queue — what to do next, what's blocked, what's pending.

```yaml
# .ai/state/next-task.yaml
tasks:
  - id: TASK-001
    description: Design SVP platform architecture
    priority: P0
    status: IN_PROGRESS
    depends_on: []
    assigned_to: architect
    mode: ARCHITECTURE
  - id: TASK-002
    description: Create framework taxonomy documents
    priority: P0
    status: PENDING
    depends_on: [TASK-001]
    assigned_to: verifier
    mode: IMPLEMENTATION
```

### 2.6 Session State

**Location:** `.ai/state/session.yaml` (machine) + `.ai/sessions/active.md` (human)

**Purpose:** Active session tracking — who's operating, in what mode, using which model, what's been touched.

```yaml
# .ai/state/session.yaml
session:
  id: ses_abc123
  status: ACTIVE
  agent: architect
  mode: ARCHITECTURE
  model: qwen-3.7-max
  started_at: 2026-07-08T10:00:00Z
  state_files_read:
    - project.yaml
    - framework.yaml
    - repository.yaml
    - next-task.yaml
  files_created: []
  files_modified: []
  last_activity: 2026-07-08T10:30:00Z
```

## 4. State Synchronization Strategy

### 4.1 Read Strategy

At session start:
1. Read ALL machine state files from `.ai/state/`
2. Read human state files from root (PROJECT_STATE.md, NEXT_TASK.md)
3. Parse human state to extract structured data
4. Compare human state with machine state
5. If mismatch, machine state wins (machine is source of truth)
6. Log any discrepancies

### 4.2 Write Strategy

During session:
1. Update machine state files as work progresses
2. Write to disk on every significant state change
3. Do NOT write human state files during session (write at end)

At session end:
1. Finalize all machine state files
2. Regenerate human state files from machine state
3. Write updated `session.yaml` with status: COMPLETED
4. Commit all state files to repository

### 4.3 Conflict Resolution

| Conflict | Resolution |
|----------|-----------|
| Machine and human state disagree | Machine state wins |
| Two agents modified the same file | Last commit wins (Git resolves) |
| State file is corrupted | Regenerate from last known good version in Git |
| Human updated human state directly | Machine detects mismatch on next read, updates machine from human for unknown fields |

### 4.4 State File Commit Rules

| File | Commit Trigger | Committer |
|------|---------------|-----------|
| `project.yaml` | Phase change, task completion | Agent |
| `framework.yaml` | Document add/remove/status change | Agent |
| `engagement.yaml` | Gate passage, evidence/finding count change | Agent |
| `repository.yaml` | Repository scan (periodic) | Tooling script |
| `next-task.yaml` | Task completion, priority change | Agent |
| `session.yaml` | Session start, activity, end | Agent |

---

## 5. State Recovery

### 5.1 Session Crash Recovery

If a session ends abnormally:
1. Next session reads `session.yaml` — detects `status: ACTIVE`
2. Marks previous session as `CRASHED` with timestamp
3. Reads all state files from disk (last committed state)
4. Lists files created/modified during crashed session (from `files_created` in session.yaml)
5. Verifies which changes were actually committed
6. Agent resumes from last committed state

### 5.2 State Corruption Recovery

If a state file is corrupted:
1. Detection: YAML/JSON parse failure on read
2. Recovery: Checkout last known good version from Git
3. Log: Corruption event recorded in repository.yaml
4. Analysis: Human reviews to determine cause

## 6. State Access Patterns

| Operation | Read | Write | Frequency |
|-----------|------|-------|-----------|
| Session start | All state files | Nothing | Per session |
| Task progress | next-task.yaml, engagement.yaml | next-task.yaml | Per task |
| Phase change | project.yaml | project.yaml | Per phase |
| Document change | framework.yaml | framework.yaml | Per document change |
| Gate passage | engagement.yaml | engagement.yaml | Per gate |
| Session end | Nothing | All state files | Per session |
| Repository scan | Everything | repository.yaml | Periodic (daily) |
