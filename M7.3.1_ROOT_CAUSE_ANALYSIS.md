# M7.3.1 — Root Cause Analysis & Quality Hardening Strategy
## Root Causes of Retrieval Degradation & Target Solutions
**Milestone:** `M7.3.1`  
**Status:** Root Cause Confirmed  
**Date:** `2026-08-20`

---

## 1. Root Cause 1: Uniform RRF Weighting Diluting Exact Identifiers

### Observation
In standard Reciprocal Rank Fusion ($k=60$) with static weights $w_{\text{lex}} = 1.0, w_{\text{vec}} = 1.0$, an exact project match at Lexical Rank 1 receives a score of $1/61 \approx 0.01639$. If an unrelated chunk happens to appear at Lexical Rank 2 ($1/62 \approx 0.01613$) and Vector Rank 2 ($1/62 \approx 0.01613$), its combined score becomes $0.03226$, completely displacing the true Rank 1 exact identifier hit.

### Root Cause
Equal weighting of lexical and semantic vector streams on structured engineering queries allows generic semantic proximity to override high-precision deterministic keyword matches.

### Solution
Implement **Query-Type-Aware Adaptive RRF Weighting**:
- When the query contains an explicit engineering identifier (`projectNumber`, `partNumber`, `machine`, `material`):
  $$w_{\text{lex}} = 2.5, \quad w_{\text{vec}} = 0.6$$
- When the query is purely conceptual / semantic:
  $$w_{\text{lex}} = 1.0, \quad w_{\text{vec}} = 1.5$$

## 2. Root Cause 2: Missing Provenance Extraction on Secondary Tables

### Observation
In tables like `part_list`, `process_planning`, and `document_index`, the project number is encoded in the file name `source_file` (e.g. `BM454 Veedol 600ml...Partlist.xlsx`) or foreign key `project_id`. When `EngineeringNormalizerService` read `row.project_number`, it found `null`, causing the resulting chunks to lack `projectNumber: 'BM454'`.

### Root Cause
Column mapping did not inspect `source_file` or foreign key relationships to populate `projectNumber`, `customer`, `machine`, and `revision` fields.

### Solution
Harden `EngineeringNormalizerService` and `EngineeringLexicalSearchService` to extract project prefixes and customer metadata from `source_file` and relational links.

---

## 3. Root Cause 3: Reranker Boost Calibration

### Observation
The reranker boost for exact project matching ($+0.30$) was sometimes insufficient to overcome rank penalties introduced during unweighted fusion.

### Solution
Increase exact project boost to $+0.35$ and ensure authority weighting (`AUTHORITATIVE_RELEASE` vs `SUPERSEDED`) scales proportionally without burying relevant active working parts.
